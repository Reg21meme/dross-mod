# Making a new boss: the step-by-step guide

How to add a new boss or mini-boss to the Dross, from design candidates to the user's pick, so it goes the same way every time. Written from the Cinder Colossus and the Rat King. Read `CLAUDE.md` first: it has the areas, the rules (shared files are add-only, colours come from `DrossColors`, `/dross` command names) and the plan.

The process has two halves:
1. **The design round.** Make several candidate looks with all their animations. Check them yourself on preview pictures, put them in the game as a frozen showcase, and let the user pick.
2. **The fight.** Build the picked design's fight only after the pick, as a separate request.

**Nothing is committed until the user has picked.**

---

## 0. Before you start

- **Do the design work yourself, in the main session**, not in a subagent: the user asked for this with the Rat King so the designs get the strongest model at full effort. Subagents are fine for searching the code.
- **Ask every question up front, in one round** (the user often leaves while you build). Typical questions:
  - **The look:** species, outfit, props, colours. Each boss serves one necromancer and uses that necromancer's colours, never the Dross blue: Fire is lava orange and obsidian; Plague is poison green, decaying reds and bone beige; Ice is pale blues and white.
  - **Size:** width, depth and height in blocks.
  - **Candidates:** how many, and what varies between them.
  - **Animations:** which ones.
  - **Minions:** what kinds, how many looks each, which animations.
  - **Names:** the boss's id in `snake_case` (`rat_king`) and the showcase command names (rule 9: `/dross showcase boss_designs <boss>`; minions get their own kind, like `/dross showcase rats`).
- **Write the plan with the candidate concepts in it** (a table: name, fur or skin, crown or head, outfit, prop, posture), so the user can adjust them before you build. Give every candidate a working name and a sign mood of at most 15 characters.
- **Check for other Claude sessions** (the `ListAgents` tool, or running `java.exe`/`gradlew` processes). If another session is working in the project folder, ask to work in a **separate linked copy** (a git worktree, for example `git worktree add ../MyMinecraftMod-<boss> -b <boss>-designs main`). Builds, test worlds and the game then don't collide, and their commits can't sweep in your unpicked work. The copy's first Gradle build sets itself up (about a minute); its first `run*` task downloads assets and may time out once: run it again.

## 1. The generator: `tools/<boss>/` (Python)

Models, textures, animations and previews are **generated by Python**, never drawn by hand. Copy the layout of `tools/ratking/`:

```
tools/<boss>/
  build.py          # entry point: builds everything (flags below)
  README.md         # what it makes, how to run it, how to change a design
  <boss>kit/        # your own modules (don't name the folder "kit" or "designs": those are tools/golems' packages)
  <boss>designs/    # one module per candidate (+ one for the minions)
```

`build.py` puts `tools/golems` on `sys.path` and **reuses the golem kit** (`tools/golems/kit/`):

| Module | What to reuse |
|---|---|
| `geo` | `Model`, `Bone`, `Cube` (box UV, whole-number sizes ≥ 1), `pack_uv`, `to_json`, `pose_matrices`, `point`, `direction`, `aim`, `euler_bedrock`. It's GeckoLib 4's exact maths. |
| `ik` | `Limb`, `Joint`, `solve` (planting feet, a staff's tip, a hand on a spot) and `bake_rest` |
| `noise` | `fbm`, `warp`, `voronoi`, `hash_float` (texture patterns) |
| `paint` | `TexelMap`, `paint_model`, `palette`, `pick`, `rgba`, `bevel` |
| `anims` | `Pose`, `Animation` (`add`, `bake`, `sample`), `to_json(prefix=...)`, `Rig` (IK with warm starts), easing (`ramp`, `bump`, `smooth`, `wobble`), `gait_offset` |
| `moves` | `keyed` (keyframed values with easing) |
| `render` | `camera`, `diffuse`, `composite`, `view_bounds`, `_draw_grid`, `_draw_figure` |
| `checks` | `fix_coplanar` (z-fighting), `stance` |
| `previews` | `font` |

The Rat King's own modules are a good starting point (`tools/ratking/ratkit/`):

| Module | What it does |
|---|---|
| `rig.py` | An upright skeleton (`RatBody` proportions and posture), rest-pose solving (`pose_rest`: spine, head, arms, free hand by IK, staff, legs by IK, tail and cape), world-direction helpers (`set_rest_world`, `aim_axis` with angle continuity, `rotate_body_about`), the cape **drape solver** (hangs each segment by gravity and swings it clear of the body) and `clamp_above` (keeps tails and capes on the ground). |
| `parts.py` | The body parts, crowns, staffs and extras, plus the **hidden-part trick** (below). |
| `fur.py` | Material painters: fur with strands, belly, outline and patterns; skin; ears with a rounded cutout; eyes with a red rage texture; cloth with folds, ragged hems, moth holes, trims and split backs; metal, rust, gems, flames, wax, wood, bone, tin, dirt, a hole. |
| `king_anims.py` | The animations, with secondary motion for capes, tails, chains and ribbons, `place()` (lets a staff or crown leave the hand and lie on the ground), and `record()` (warm-up laps make loops seamless). |
| `quad.py`, `rat_anims.py` | A four-legged minion skeleton and its idle and run. |
| `views.py` | Previews **clipped at the ground** (burrowing reads right), cut-out transparency, particle sketches (Zzz, steam), and the `fit`, `grid`, `label` and `page` layout helpers. |
| `javagen.py` | Writes the Java design lists. |

**Designs.** Each candidate is a module with:
- `NUMBER`, `LABEL`, `ID` (no underscores), `NAME`, `MOOD` and `BLURB`;
- `body()`: proportions and posture;
- `build(m, B, b)`: boxes;
- `build_staff()` if it has a measured prop;
- `materials()`: `{name: painter}`;
- `STYLE`: which walk, sleep and gesture it uses.

Keep every tuning number a labelled constant.

**Outputs:**
- **Assets:** `src/main/resources/assets/dross/{geo,animations,textures}/entity/<boss>/<id>...`, with a `<id>_glow.png` for full-bright parts and any extra layer textures (the Rat King's `<id>_rage.png` red eyes).
- **Java:** the generated design list(s) in `src/main/java/com/reg21meme/dross/boss/<boss>/` (marked "don't edit by hand").
- **Previews:** in **`boss-previews/<boss>/`**. Every boss has its own folder, and minions go in a subfolder (`boss-previews/rat_king/rats/`).

**Flags:**

| Command | What it does |
|---|---|
| `build.py` | everything |
| `build.py --kings 1 3` | only those candidates (no Java) |
| `build.py --rats` | only the minions |
| `build.py --previews-only` | previews only |
| `build.py --quick <dir> [n]` | quick still views |
| `build.py --sheet <dir> [n]` | one candidate's full sheet |
| `build.py --frames <dir> <n> <anim> <yaw> <scale> <t>...` | big frames of one animation |
| `build.py --clip 1 4` | only the clipping check (props, ears, body, floor in every animation) |
| `sounds.py` | every sound, the sound list and the listening page |

A full Rat King build takes about 15 minutes (the clipping check and the staff guard run on every frame).

## 2. Check the previews yourself (the review loop)

The previews use GeckoLib's own maths, so they match the game. **Look at every one** (the Read tool shows PNGs) and iterate until each reads clearly. Use `--quick` and `--frames` into the session's scratchpad while iterating, and write the final previews into `boss-previews/<boss>/`.

What to check, every round:
- **Size and silhouette:** the build prints each candidate's measured size. Each design should be recognisable from the front, side and back.
- **Nothing clips:** capes through rumps, tails through capes, props through heads, arms through torsos. Fix the geometry, or let the solvers keep things apart (capes are draped against the body boxes, which are found by tag: accessories don't count). Use the clipping helpers (`kit.clipping`) for a numeric check.
- **Nothing hangs in the air or sinks into the ground.** Rest-pose IK warnings ("misses its footprint by N units") mean a leg can't reach. Fix the anatomy, give the solver better starting bends, or let the footprint move (`quad.pose_rest` searches nearby spots).
- **Every animation, frame by frame** (the sheet's filmstrips):
  - The start and end match the pose the next animation starts from.
  - Loops are seamless.
  - Feet don't slide.
  - Nothing pokes out of the ground early (a prop held upright while underground).
  - Particles appear where the markers are.
- **At night:** only what should glow glows.

## 3. The Java (boss area: `com.reg21meme.dross.boss.<boss>`)

Copy `boss/ratking/`.

- **The entity** (`RatKing`: `Monster` + `GeoEntity`):
  - **Synced data:** design number, action (an enum like `RatKingAction`), an **action counter** that goes up on every start (so a repeat restarts the animation), and a showcase flag (plus any look state, like enraged).
  - **Animation:** one GeckoLib controller. When the counter changes, call `forceAnimationReset()`. Loops use `thenLoop`, everything else `thenPlayAndHold`.
  - **Timing:** the server ends timed actions (an animation that plays once goes back to idle). A save made mid-action loads as its end state.
  - **Client particles** are timed from the generated tables against `tickCount - clientActionStart - BLEND`.
  - **Showcase rules:** no AI, silent, persistent, `isInvulnerableTo` except damage that bypasses invulnerability (`/kill`), not pushable, survives Peaceful. Right-click steps through the animations, sneak + right-click dies.
  - Enlarge `getBoundingBoxForCulling` if it lies down or reaches far.
- **The client** (`boss/<boss>/client/`):
  - A `GeoModel` that picks each design's files by its id.
  - A `GeoEntityRenderer` with `GeoRenderLayer`s for the glow textures (`RenderType.entityTranslucentEmissive`, full bright, alpha for fades).
  - **Marker bones:** bones with no boxes, like `zzz` and `ear_l_steam` with a sibling `ear_l_steam_aim`. Set `setTrackingMatrices(true)` on them in `preRender` and read `getWorldPosition()` in `postRender`, straight after drawing. **GeckoLib shares bones between every entity using the same model.**
  - A custom particle: a `TextureSheetParticle` plus provider, `particles/<name>.json`, and a sprite drawn by the generator.
  - Register everything in a `@Mod.EventBusSubscriber(bus = MOD, value = Dist.CLIENT)` class.
- **Shared files (add only):**
  - `registry/ModEntities`: `EntityType`s sized to the measured model.
  - `registry/ModParticles`.
  - An attributes subscriber (`EntityAttributeCreationEvent`): placeholders until the fight.
  - `en_us.json`: `entity.dross.<id>` and the showcase's action-bar lines.
  - `DrossColors`: the showcase buttons' colour, in the World site section.

## 4. The showcase commands (`command/`)

- `/dross showcase boss_designs <boss>`: copy `command/RatKingShowcase.java`.
  - A row of frozen designs facing you.
  - A post and wall sign each ("No. N", name, mood). Signs hold 15 characters a line, and `build.py` checks this.
  - The floor is cleared and flattened, and running it again replaces the row.
  - A `Control` enum gives one subcommand per animation (`/dross showcase boss_designs <boss> rage`) and **clickable chat buttons** (`ClickEvent.RUN_COMMAND`).
- Minions: copy `command/RatShowcase.java` (pedestals with signs, both kinds in one row, controls).
- Sounds: `/dross showcase boss_sounds <boss>` (copy `command/RatSoundShowcase.java`) lists every sound in chat with a
  [play] button (`/playsound`), from the generated list (`boss/ratking/RatKingSounds`).
- Wire both into `DrossCommand.register()` (next to `colossusDesignShowcase()`), and add the new paths and controls to `DrossCommandGameTest` (`NEW_COMMANDS`, plus one loop per `Control` enum).

## 5. Tests

- **A GameTest class:** copy `boss/ratking/RatKingShowcaseGameTest`. It uses the Colossus arena (`ColossusGameTest.ARENA`, `waitForArena`). Check that:
  - every design spawns as a showcase;
  - ordinary damage doesn't hurt it;
  - the death leaves it lying there;
  - timed actions end in the right state;
  - state flags switch;
  - minions spawn as the right kind.
- **Build:** `.\gradlew.bat build --console=plain`.
- **Headless:** `.\gradlew.bat runGameTestServer -PgameTestWorld=<new folder> --console=plain`. Look for **"All N required tests passed :)"** (a datapack failure can still exit 0).

## 6. The in-game photo check (before handing over)

The previews can drift from the game, so check the real thing:
1. Copy `tools/photo_booth/PhotoBooth.java.template` into the boss's client package. It's gated by an environment variable and runs a script. It:
   - creates a creative superflat world;
   - runs the showcase commands;
   - teleports to viewpoints, holding the camera every tick;
   - plays every control and takes screenshots (`run/screenshots/`);
   - leaves the rows standing and quits.
2. Edit its script for your rows.
3. Set `pauseOnLostFocus:false` in `run/options.txt`, then launch with `$env:DROSS_RAT_PHOTOS="1"; .\gradlew.bat runClient --console=plain` (rename the variable for your boss).
4. Read the shots and compare them with the previews: orientation, UVs, glow and extra layers, particles, hidden parts.
5. Afterwards:
   - delete the class and `run/screenshots/`;
   - restore `options.txt`;
   - rebuild.

   Keep the world: it's ready for the user.

## 7. Hand over

- Launch `.\gradlew.bat runClient --console=plain` in the background (it blocks until the game closes).
- Tell the user:
  - which world to open (the photo-check world), or to make a superflat world with cheats on;
  - the commands to run;
  - that they can click the chat buttons or right-click a design (sneak + right-click: it dies);
  - where the previews are.
- **Don't commit.** Wait for the pick.

## 8. After the user picks

- Record everything in `CLAUDE.md`:
  - a plan step: the candidates, the pick and why, what's built and what's left;
  - the Areas table;
  - **"Verify over time"** lines for whatever wasn't seen in-game;
  - the user's rules for the look.
- Update `.claude/agents/boss-builder.md` (and `world-builder.md` for the commands) and `README.md`.
- Optionally drop the losing candidates from `build.py` and archive them: `tools/<boss>/designs/round1/` and `boss-previews/<boss>/round1/`.
- Commit on the branch, then merge into `main` when the user says so. The fight is the next request.

## Lessons learned (pitfalls)

- **Euler angles must stay continuous.** GeckoLib blends rotation keyframes angle by angle, so a jump from 179° to -179° spins a part all the way round. Every rotation computed from a matrix (`geo.euler_bedrock`, `rig.aim_axis`) must get the previous frame's angles (`prev=`). Staffs and crowns that fly through odd angles in the previews are this bug.
- **Order inside a frame matters.** Place a detached prop (`place()`) after every arm change of that frame, or it moves with the hand afterwards.
- **Blend, don't overwrite.** A helper that sets a pose at strength 0 must leave the bone alone (`set_limb_totals` blends from the current value).
- **The hidden-part trick.** Parts that appear only sometimes are built inside the body or under the ground, and the animations slide them out: eyelids, cartoon X eyes, a tongue, a dirt hole. Nothing needs switching on and off in Java, and the previews show it as the game does.
- **Box sizes are whole numbers ≥ 1** (box UV). Small creatures get chunky; use pale, thin details (1-unit whiskers look like extra limbs if they're dark).
- **Alternate a tiny inflate on chain segments** (tails, cape panels), so straight runs don't z-fight in their overlap.
- **Two-segment legs can't reach every spot** with the foot flat. Let the footprint move, or add a joint.
- **Big decals don't belong on the ground plane**: a box face exactly at y = 0 z-fights with the ground. Hide them at y ≤ -1 and raise them to sit on top.
- **Separate linked copy plus no early commits** keeps parallel sessions from colliding.
- **Check props against the body in every frame, by numbers.** The user spotted ears passing through the staff and the
  staff sinking into the floor while he slept. `ratkit/clip.py` samples every animation as the game plays it and
  reports each clash (staff through ears, head, crown, body, cape; anything through the floor), and `ratkit/guard.py`
  fixes the staff frame by frame (tilting it about the grip, sliding it through the fist, or lifting a loose one),
  easing the correction in and out so nothing jumps. A prop that lies beside the boss (the staff while he sleeps)
  gets its spot searched for (`staff_bed`): the nearest clear spot to the preferred one, for each body build.
- **Model space versus the game's facing.** `pose_matrices(pose, yaw_deg=0.0)` turns the model round the way the game
  shows it (front +z); the hole, the hands' targets and every other model-space spot use `pose_matrices(pose)` (front
  -z). Mixing the two makes a check (or a placement) look at the wrong side of the boss.
- **Put markers where the action is.** A burrow's dirt mound goes where the head goes into the ground, and the whole
  body should go down through it (slide the body along its own axis through one entry point); the pop-up comes back
  up through the same hole.
- **Sounds can be original too.** `tools/ratking/sounds.py` synthesizes every sound (a small vocal tract with vowels
  for voices, squeaks, a chime train whistle, knocks, thuds, whooshes, reverb) and writes the `.ogg` files (needs
  `pip install soundfile`), the `sounds.json` events, the subtitles and a list for `/dross showcase boss_sounds <boss>`.
  You can't listen, so check each sound's spectrogram and loudness over time instead. Give future attacks several
  versions each for the user to choose from, and play the showcase's animation sounds with `level.playSound(null, ...)`
  so silent showcase entities still make them.
