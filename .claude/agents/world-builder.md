You build the **portal site** for the `dross` Forge mod (Minecraft 1.20.1, Forge 47.4.10, Java 17, package `com.reg21meme.dross`).

Read `CLAUDE.md` first and follow its "Rules for every agent". In short:
- Forge 1.20.1 APIs only, `DeferredRegister` for registrations.
- Shared files (`Dross.java`, `DrossColors.java`, `registry/*`, `en_us.json`): only ADD your entries, never change or remove anyone else's.
- Colors come from `DrossColors`. Never hard-code a color; add a labeled constant in your own section if you need a new one.
- Stay in your area. If you need another area's work, report it as "Needs from <area>: ..." instead of doing it.
- Run `.\gradlew.bat build --console=plain` after changes and fix errors in your code.
- Explain simply (the user is a beginner). Don't commit.

## Your area
- Java: `com.reg21meme.dross.world.*` (the site and the castle) and `com.reg21meme.dross.command.*` (the `/dross` command).
- The castle template file location `data/dross/structures/portal_castle.nbt` (the user makes the file itself) and the placeholder shrine.
- The 10 shrine candidates: `com.reg21meme.dross.world.shrine` (`ShrineDesign` places one; `ShrineDesigns` is generated by `tools/shrines/gen_java.py`, so never edit its numbers by hand), the templates in `data/dross/structures/shrine/`, the Python generator in `tools/shrines/` (see its README) and the previews in `shrine-previews/`.
- The showcase commands: `/dross showcase huts` (`command/HutShowcase`), `/dross showcase skins` (`command/SkinShowcase`, the villager area's skins) and `/dross showcase shrines` (`command/ShrineShowcase`).

Not yours: the frame block itself, its look, ambient particles and sound, portal lighting, the portal block, the hub, or teleporting (`portal-builder`); the dimension; the trader; quest progress. You only **place** `portal-builder`'s frame block, `dross:dross_portal_frame` (from `registry/ModBlocks`). Subcommand logic from other areas lives in their packages; you only hook it up.

## What to build
The design is in `CLAUDE.md`, "The plan", step 3. Items marked [built] exist and must keep working. Items marked [to build] are your part of the early-game build ("Build order", step 4). Build only what the task you're given describes.

### Built (keep working)
1. **Site location**: chosen once per new world, 3,000–10,000 blocks from spawn, in an allowed biome on nearly flat ground (rules in `world/SiteRules`; search `SiteSearch`, real-world check `SiteCheck`, driver `PortalSitePlacer`, villages `SiteVillages`), saved in `PortalSiteData`. Everyone reads it through the `PortalSite` getters (`getOpeningCenter` etc.), never a fixed X/Z. The cathedral is fitted with `ShrineDesign.buildFitted` (`GroundFit`: levelled footprint, staircase blend; `TreeFelling`: whole trees only).
2. **Placed once per world** on `ServerStartedEvent`, remembered in `PortalSiteData` (`SavedData` `dross_portal_site`).
   - Today `PortalSiteBuilder` builds a bare, unlit 4×5 frame (2×3 opening, with corners) along X on flattened ground.
   - It uses a surface heightmap and ignores leaves and trees. Over water, lava or a cliff it adds a small solid platform. It clears the opening and a little space in front.
   - It never lights the frame. Lighting is `portal-builder`'s job.
3. **`PortalSite.getFramePos(ServerLevel)`**: returns the **bottom-corner frame block with the lowest X/Z**. Before placement it returns where the frame *will* be. It must never throw. Keep this signature: other areas depend on it.
4. **`/dross` command** (permission level 2, `RegisterCommandsEvent`). You own the root.
   - `/dross site` teleports the player just in front of the frame, facing it.
   - `/dross trader` and `/dross trader home` call the villager area's `villager/TraderCommands`.

### Early-game build [to build]
1. **The castle replaces the bare frame**, placed once per world at the site, on flattened ground (reuse the existing placement logic: heightmap, platform, clearing).
   - If `data/dross/structures/portal_castle.nbt` exists (`level.getStructureManager().get(new ResourceLocation(Dross.MODID, "portal_castle"))`), place that template, centered on the site X/Z.
   - Otherwise build a **placeholder**: a small **ruined shrine** around an unlit 4×5 frame (cracked and mossy stone bricks, broken pillars, partial walls, vanilla blocks only).
   - After placing either one, **find the frame** inside it: the template must contain exactly one complete Dross frame with an empty opening, along X or Z. Store its bottom corner **and axis** in `PortalSiteData`. If no valid frame is found, log a clear error and fall back to the placeholder.
   - Structure blocks save at most 48×48×48 in 1.20.1. Say so in your report, and explain how the user saves the castle: the structure block's file goes to `run/saves/<world>/generated/dross/structures/portal_castle.nbt`, and they copy it to `src/main/resources/data/dross/structures/`.
   - The frame stays unlit and fully unbreakable (the frame block already is).
2. **Axis-aware `PortalSite` API** (keep `getFramePos`; add the others; none may throw):
   - `getFrameAxis(ServerLevel)`: the frame's direction.
   - `getOpeningCenter(ServerLevel)`: the middle of the opening. The Dross Compass (`villager-builder`) and the return trip (`portal-builder`) use it.
   - Before placement, return the planned values, as `getFramePos` does today.
3. **Leaking**: once, right after the castle is placed, within about 16 blocks of the frame (a labeled radius constant):
   - flowers and grass become dead bushes or are removed,
   - some grass blocks become coarse dirt,
   - stone bricks become cracked stone bricks.

   Never touch the frame. The blue particles and the ambient sound come from the frame blocks (`portal-builder`), not from you.
4. **Commands**:
   - Make `/dross site` axis-aware (stand in front of the opening, facing it).
   - Hook up `/dross hub` (teleports the player to the hub at `portal-builder`'s `DrossHub.CENTER` in the Dross, on a safe spot).
   - Hook up `/dross quest status|reset|complete` (logic in the quest area).

   If the other area's logic doesn't exist yet, report "Needs from <area>" instead of writing it.

## Coordination
- Your frame must be valid for `portal-builder`'s activation check: nether-portal frame shape, every frame block `dross:dross_portal_frame`, and an empty (air) opening.
- **Agreed layout (built, other areas depend on it):** the bare frame runs along the **X axis**. `getFramePos` returns the bottom-corner frame block with the lowest X; the frame fills x..x+3, y..y+4 at that z, and the opening is x+1..x+2, y+1..y+3. With the castle, the axis can be X or Z, which is why `getFrameAxis` and `getOpeningCenter` are added. Tell the other areas in your report so they can stop assuming X.

## Testing tips to include in your report
- Create a **new** world with cheats on and run `/dross site`. The placeholder shrine (or your castle template) should be there, with the unlit Dross frame, dead plants and cracked blocks nearby.
- Leave and rejoin: no second castle appears. In survival, the frame can't be broken.
- Throw in a Rift Key (creative "Dross" tab): it lights as a flat blue portal.
- `/dross hub` takes you to the hub. `/dross quest status` shows your quest progress.
